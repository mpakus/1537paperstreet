# 1537paperstreet — план разработки

> Быстрый Markdown-редактор и ридер для macOS на Rust.
> Домен: **1537paperstreet.org** · Bundle ID: `org.paperstreet1537.app`

---

## 1. Обзор

**Что это.** Локальное десктопное приложение для macOS: открывает Markdown-файлы из «проектов» (папок на диске), рендерит их с поддержкой Mermaid, тем и настраиваемой типографики, позволяет редактировать их и управлять файлами внутри проекта.

**Чего в продукте нет и не будет в v1:** аккаунтов, облака, телеметрии, сетевых запросов (кроме проверки обновлений, которую можно выключить), плагинов.

## 2. Ключевые технические решения

Формат: **решение → альтернативы → почему так**. Каждое решение оформляется как ADR в `docs/adr/`.

### ADR-001. Оболочка: Tauri v2, а не чистый Rust-GUI и не Electron

- **Решение:** Tauri v2, WKWebView как рендерер, вся логика — в Rust.
- **Альтернативы:** `egui` / `iced` / `GPUI` (чистый Rust); Electron; нативный Swift + AppKit.
- **Почему:** Mermaid — это JS-библиотека, и надёжной нативной реализации на Rust нет. В чистом Rust-GUI пришлось бы тащить JS-движок (`deno_core`/`rquickjs`) плюс собственный SVG-рендерер — это больше кода, больше памяти и хуже качество, чем WKWebView, который в macOS уже загружен в память системой. Аргумент усилился с добавлением редактора: CodeMirror 6 даёт зрелый текстовый редактор с виртуализацией, IME, композицией и системной проверкой орфографии — на чистом Rust это месяцы работы. Electron отпадает по памяти и размеру (~150 MB против ~18 MB).
- **Цена решения:** IPC-граница между Rust и UI; нет WebDriver для WKWebView (влияет на E2E-тесты, см. § 14.5); нужно вручную защищаться от XSS в пользовательском Markdown.

### ADR-002. Markdown-парсер: `pulldown-cmark`, а не `comrak`

- **Решение:** `pulldown-cmark` с включёнными GFM-опциями.
- **Почему:** самый быстрый CommonMark-парсер в экосистеме, pull-based (итератор событий) — позволяет **на лету** перехватывать события: подменять fenced-блоки Mermaid, переписывать относительные пути, собирать TOC. Отдельно важно для редактора: `Parser::into_offset_iter` даёт байтовые смещения каждого события, а это фундамент инкрементального рендера и синхронного скролла (§ 9.6, § 9.7).
- **Опции:** `ENABLE_TABLES | ENABLE_FOOTNOTES | ENABLE_STRIKETHROUGH | ENABLE_TASKLISTS | ENABLE_SMART_PUNCTUATION | ENABLE_HEADING_ATTRIBUTES | ENABLE_MATH | ENABLE_GFM | ENABLE_YAML_STYLE_METADATA_BLOCKS | ENABLE_DEFINITION_LIST | ENABLE_WIKILINKS`.
- **Что теряем:** часть расширений comrak по-прежнему требует собственных пассов (YAML front matter рисуется как `<dl class="front-matter">`, wiki-ссылки резолвятся в файлы проекта). Backlinks — отдельная задача, не v1.

### ADR-003. Подсветка кода — `syntect` с **классовым** выводом, не инлайновыми стилями

- **Решение:** `ClassedHTMLGenerator` → `<span class="hl-kw">`, цвета задаются CSS-переменными темы.
- **Почему:** смена темы становится изменением одной CSS-переменной вместо повторного рендера всего документа. Это то, что укладывает «переключение темы» в бюджет 16 ms.
- **Детали:** `syntect` без `onig` (фича `regex-fancy`, чистый Rust — не тянем C-зависимость); `SyntaxSet` грузится лениво при первом блоке кода и живёт в `OnceLock`.

### ADR-004. Фронтенд: Svelte 5 + Vite + TypeScript

- **Почему:** компилируется в прямые DOM-операции, нет runtime virtual DOM. Итоговый JS-бандл ~30–40 KB против ~140 KB у React.
- **Правило:** UI — «тонкий». Ни одного бизнес-правила во фронтенде. Всё, что можно посчитать в Rust, считается в Rust. Исключение — редактор: работа с текстовым буфером живёт в CodeMirror, см. ADR-008.

### ADR-005. Формат передачи документа: готовый HTML, а не Markdown

- **Решение:** Rust отдаёт в WebView уже отрендеренный, санитизированный HTML чанками.
- **Почему:** парсинг Markdown в JS — это 10–50× медленнее и десятки мегабайт JS-библиотек. Так тяжёлая работа остаётся в нативном коде, а WebView работает «тупым» рендерером.

### ADR-006. Удаление файлов — в Корзину macOS, не `unlink`

- Крейт `trash`. Пользователь может отменить действие штатными средствами системы. Безвозвратное удаление — только по явному Shift-подтверждению.

### ADR-007. Не используем App Sandbox в v1

- **Почему:** приложению нужен произвольный доступ к папкам проектов. Sandbox потребовал бы security-scoped bookmarks для каждого пути и заметно усложнил бы файловые операции.
- **Следствие:** дистрибуция вне Mac App Store — Developer ID + нотаризация + DMG (и Homebrew cask).

### ADR-008. Редактор: CodeMirror 6

- **Решение:** CodeMirror 6, загружается динамическим импортом при первом входе в режим редактирования.
- **Альтернативы:** Monaco (~5 MB, движок VS Code — избыточен, тяжёлый старт); голый `<textarea>` (нет подсветки, нет управления курсором, нет виртуализации); собственный редактор на `contenteditable` (это ловушка: IME, композиция, undo, выделение — годы чужих багов); нативный `NSTextView` через FFI (не сочетается с WebView-превью).
- **Почему:** модульный и tree-shakeable (в бандл попадает только нужное, ~180 KB gzip), виртуализирует вьюпорт (документ 10 MB не тормозит), корректно работает с IME и композицией, даёт готовые undo/redo, поиск, множественные курсоры, и подсветку Markdown из коробки.
- **Цена:** текстовый буфер живёт в JS, а не в Rust. Это сознательное отступление от правила «логика в Rust» — переносить буфер в Rust означало бы гонять весь текст через IPC на каждое нажатие клавиши.

### ADR-009. Запись файлов: атомарно, с сохранением характеристик файла

- **Решение:** запись во временный файл в той же директории → `fsync` → `rename`. Сохраняем права доступа, наличие BOM, тип переносов строк, наличие финального перевода строки.
- **Почему:** запись поверх файла — это окно, в котором отключение питания оставляет пользователя без данных. `rename` в пределах одной ФС атомарен. Сохранение EOL и BOM критично для файлов из git-репозиториев: иначе первое же сохранение даёт diff на весь файл.
- **Дополнительно:** если байты буфера не отличаются от байтов на диске — не пишем вообще. Это убирает лишний износ диска и ложные срабатывания watcher'а.

### ADR-010. Живое превью — инкрементальный рендер по блокам

- **Решение:** документ разбивается на блоки верхнего уровня с байтовыми диапазонами; каждый блок хешируется; при правке пере-рендерятся только блоки с изменившимся хешем, DOM патчится по индексу блока.
- **Почему:** полный ре-рендер документа на 1 MB занимает ~50 ms, и на каждом нажатии клавиши это гарантированный лаг. Инкрементальный подход даёт ~3–8 ms на типичную правку внутри абзаца.
- **Инвариант:** результат инкрементального рендера **побайтово равен** полному. Проверяется property-тестом. При расхождении — автоматический фолбэк на полный рендер и запись в лог.

### ADR-011. История: собственный snapshot-store, а не git

- **Решение:** глобальное content-addressed хранилище (blake3 + zstd) с индексом на проект в SQLite. Git-бэкенд отложен в v1.1.
- **Альтернативы:** теневой git-репозиторий через `GIT_DIR` + `GIT_WORK_TREE`; коммиты в репозиторий пользователя в приватный ref `refs/1537paperstreet` через временный индекс; `gix` (gitoxide) как встроенная реализация git.
- **Почему:** большинство папок с заметками — не репозитории, а история, которая работает только у части пользователей, это не история, а лотерея. Плюс `/usr/bin/git` на чистом Mac — заглушка, обращение к которой открывает установщик Xcode CLT; зависеть от внешнего бинарника в горячем пути нельзя. `gix` дал бы независимость, но стоит несколько мегабайт бинарника при бюджете DMG в 22 MB.
- **Что теряем:** история не инспектируется штатным `git log`. Компенсируется командой «Экспортировать историю в git-репозиторий» (§ 10.8).
- **Что выигрываем сверх задачи:** снимок на `base_hash` даёт общего предка для трёхстороннего разрешения конфликтов (§ 10.6).

### 3.3. Контракт IPC

Все команды описываются один раз в Rust и генерируют TypeScript-типы через `ts-rs` (или `specta`). **Ручное дублирование типов запрещено** — это главный источник рассинхронизации.

| Команда                                                | Аргументы                                              | Возврат                                  |
| ------------------------------------------------------ | ------------------------------------------------------ | ---------------------------------------- |
| `config_get` / `config_set`                            | — / `Config`                                           | `Config` / `()`                          |
| `projects_list`                                        | `{ query?, limit, offset }`                            | `{ items: Project[], total }`            |
| `projects_add` / `projects_rename` / `projects_remove` | …                                                      | `Project` / `()`                         |
| `tree_read_dir`                                        | `{ project_id, rel_path }`                             | `TreeNode[]` (один уровень)              |
| `fs_mkdir` / `fs_create_file` / `fs_rename`            | …                                                      | `TreeNode`                               |
| `fs_copy` / `fs_move`                                  | `{ project_id, from[], to_dir }`                       | `TreeNode[]`                             |
| `fs_trash`                                             | `{ project_id, rel_paths[] }`                          | `()`                                     |
| `doc_open`                                             | `{ project_id, rel_path }`                             | `DocumentMeta` + чанки событиями         |
| `doc_source`                                           | `{ project_id, rel_path }`                             | `{ text, eol, bom, trailingNewline, encoding, writable }` |
| **`doc_save`**                                         | `{ project_id, rel_path, text, base_hash }`            | `{ hash, mtime }` или `Conflict`         |
| **`doc_stat`**                                         | `{ project_id, rel_path }`                             | `{ hash, mtime, size, writable }`        |
| **`render_incremental`**                               | `{ doc_id, text, changed_range }`                      | `{ patches: BlockPatch[] }`              |
| **`assets_import`**                                    | `{ project_id, rel_dir, bytes, mime, suggested_name }` | `{ rel_path }`                           |
| **`drafts_list` / `drafts_resolve`**                   | …                                                      | `Draft[]` / `()`                         |
| **`history_list`**                                     | `{ project_id, rel_path?, limit, before }`             | `Snapshot[]`                             |
| **`history_read`**                                     | `{ snapshot_id }`                                      | `{ text }`                               |
| **`history_restore`**                                  | `{ snapshot_id, mode: Overwrite\|CopyAside }`          | `{ rel_path }`                           |
| **`history_pin`**                                      | `{ snapshot_id, pinned, label? }`                      | `()`                                     |
| **`history_stats` / `history_forget_project`**         | …                                                      | `Stats` / `()`                           |
| **`history_export_git`**                               | `{ project_id, dest }`                                 | `{ job_id }`                             |

### 4.3. Правила работы с хранилищем (`store.rs`)

Это место, где обычно теряют пользовательские данные. Требования жёсткие:

5. **Миграции:** `migrate(from: u32) -> Result<Value>`, тест на каждую пару версий.
6. **Одна инстанция:** advisory-lock на `~/.1537paperstreet/.lock`, вторая копия приложения фокусирует первое окно.

## 5. Конвейер рендеринга Markdown

```
файл на диске
   │  read (< 8 MB → String; больше → предупреждение + режим «только исходник»)
   ▼
blake3(bytes + render_options)  ──► попадание в LRU-кэш? ──► готовый HTML
   │ промах
   ▼
pulldown-cmark::Parser::into_offset_iter (поток Event + байтовый диапазон)
   │
   ├─ Event::Start(CodeBlock(Fenced("mermaid")))
   │     → <figure class="mermaid" data-hash="…"><template>…</template></figure>
   ├─ Event::Start(CodeBlock(Fenced(lang)))
   │     → syntect ClassedHTMLGenerator
   ├─ Event::Start(Image|Link) с относительным путём
   │     → asset://localhost/<project_scope>/<rel>   (проверка выхода за корень)
   ├─ Event::Start(Heading)
   │     → id = slug(text), запись в TOC
   └─ Event::Html (сырой HTML)
         → если allow_raw_html=false: ammonia-санитайзинг
   ▼
разбиение на блоки верхнего уровня; каждый получает
   data-block="<index>" data-src-line="<line>" и собственный blake3
   ▼
группировка блоков в чанки (~64 KB) в <section class="chunk">
   ▼
чанк 1 → возврат синхронно (первый кадр)
чанки 2..n → события doc://chunk (по одному на кадр анимации)
```

**Ключевые приёмы производительности:**

- Каждый чанк получает `content-visibility:auto; contain-intrinsic-size:auto 800px`. Браузер не считает layout невидимых секций — главный рычаг для документов на мегабайты.
- Кэш: LRU в памяти (16 документов / 64 MB потолок) + дисковый кэш в `~/.1537paperstreet/cache/<blake3>.html` с очисткой по LRU и лимиту 200 MB.
- При изменении файла на диске — инвалидация по хешу, ре-рендер только изменённого документа.
- Позиция скролла сохраняется по якорю ближайшего заголовка, а не по пикселям.

## 6. Mermaid

## 7. Файловый менеджер

### 7.1. Безопасность путей — обязательный слой

Каждая операция проходит через `fsops::resolve(project_root, rel_path) -> Result<PathBuf>`:

1. Отклонить `..`, абсолютные пути, NUL-байты.
2. `canonicalize` родителя и проверить `starts_with(canonical_root)`.
3. Отклонить, если любой компонент — симлинк, ведущий за пределы корня.
4. Нормализовать имя в NFC (macOS отдаёт NFD — иначе дубликаты имён с кириллицей).
5. Запретить зарезервированные имена и имена длиннее 255 байт.

Это единственная точка входа в ФС, включая запись документов и импорт ассетов. Property-тесты (`proptest`) на попытки выхода за корень — обязательны.

### 7.2. Операции

| Операция                     | Поведение                                                                                                                      |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Создать папку/файл           | Валидация имени, конфликт → предложить `name 2`                                                                                |
| Переименовать                | Атомарный `rename` в пределах корня; открытый буфер следует за файлом                                                          |
| Копировать                   | Рекурсивно, с прогрессом для > 50 MB, конфликт → «Заменить / Оставить оба / Пропустить»                                        |
| Переместить                  | `rename` если тот же volume, иначе copy+delete с откатом при ошибке                                                            |
| Удалить                      | `trash::delete_all` (Корзина). Shift → безвозвратно, с подтверждением                                                          |
| Drag & drop                  | Внутри дерева = переместить; с ⌥ = копировать; из Finder = импорт копированием; **на другой проект в списке = переместить** (⌥ = копировать); **в редактор = вставить относительную ссылку** |
| Reveal in Finder             | ⌘⇧R                                                                                                                            |
| Открыть во внешнем редакторе | ⌘⇧O — для файлов, которые приложение не редактирует                                                                            |

### 7.3. Дерево и наблюдение за изменениями

- **Ленивое** чтение: содержимое каталога читается только при раскрытии узла. Проект с 200 000 файлов не должен ничего замедлять.
- **Виртуализация** списка: в DOM живут только видимые строки + буфер ~20.
- `notify` (FSEvents) с дебаунсом 150 ms и коалесценцией; при переполнении очереди — мягкий ре-скан только раскрытых узлов.
- Собственные записи приложения помечаются, чтобы автосохранение не поднимало событие «файл изменён извне» (иначе получим петлю).
- Сортировка: папки первыми, затем по имени с natural sort (`file2.md` < `file10.md`).

## 9. Редактор

### 9.1. Режимы

| Режим   | Что показывает                      | Переключение |
| ------- | ----------------------------------- | ------------ |
| Preview | Только рендер, только чтение        | ⌘E           |
| Editor  | Только исходник с подсветкой        | ⌘E           |
| Split   | Редактор слева, живое превью справа | ⌘⇧E          |

Режим по умолчанию — в конфиге; текущий режим запоминается на сессию для каждого файла.

**Файл открывается только для чтения**, если: не UTF-8, размер > 8 MB, нет прав на запись, определён как бинарный. В этих случаях показывается явная плашка с причиной — не молчаливое игнорирование ввода.

### 9.2. Возможности v1

- Подсветка синтаксиса Markdown, мягкий перенос, подсветка текущей строки, номера строк (опция).
- Автопродолжение списков, чек-боксов и цитат по Enter; Tab / ⇧Tab меняют уровень элемента списка.
- Автопарные скобки и кавычки.
- Форматирование выделения: ⌘B, ⌘I, ⌘K (ссылка), ⌘⇧K (инлайн-код), ⌘⇧1…6 (заголовок), ⌘⇧L (список), ⌘⇧. (цитата).
- Вставка изображения из буфера обмена → файл сохраняется в `<project>/<assets_dir>/` с именем по дате и хешу → в текст вставляется относительная ссылка.
- Перетаскивание файла из дерева или Finder в редактор → относительная ссылка (изображение → `![]`, прочее → `[]`).
- Найти и заменить (⌘F / ⌘⌥F), опционально regex.
- Undo/redo — история CodeMirror, не сбрасывается при переключении режимов.
- Множественные курсоры и системная проверка орфографии — бесплатно от платформы.

**Не входит в v1:** WYSIWYG-редактирование, vim/emacs-режимы, сниппеты, история версий, совместное редактирование.

### 9.3. Сохранение

Автосохранение срабатывает при: 800 ms без ввода · потере фокуса окна · переключении файла · закрытии окна · ⌘S.

Алгоритм записи (`docio.rs`):

1. Если байты буфера идентичны байтам на диске — **не писать вообще**.
2. Сверить хеш файла на диске с `base_hash` буфера. Не совпал → конфликт (§ 9.4), не перезаписывать.
3. Восстановить особенности исходного файла: BOM, тип переносов строк (LF/CRLF), наличие финального перевода строки.
4. Записать во временный файл в той же директории, `fsync`, скопировать права доступа, `rename`.
5. Обновить `base_hash` и снять флаг «изменён».

Индикатор несохранённых изменений — точка в дереве файлов и в заголовке окна.

**Если запись не удалась** (нет прав, диск полон, том отключён): буфер сбрасывается в черновик `~/.1537paperstreet/drafts/<blake3(abs_path)>.md` вместе с метаданными, показывается постоянный баннер с объяснением и кнопкой «Сохранить как…». Черновик не удаляется, пока файл не сохранён успешно.

**При старте** приложение проверяет каталог черновиков и предлагает восстановление: «Найдены несохранённые изменения в N файлах» → просмотр различий → применить или отбросить.

### 9.4. Внешние изменения файла

| Ситуация                             | Поведение                                                             |
| ------------------------------------ | --------------------------------------------------------------------- |
| Буфер чист, файл изменён на диске    | Тихая перезагрузка, позиция скролла и курсора сохраняются             |
| Буфер изменён, файл изменён на диске | Баннер: «Оставить мою версию / Загрузить с диска / Показать различия» |
| Файл удалён или перемещён извне      | Буфер остаётся в памяти, предложение «Сохранить как…»                 |
| Файл стал недоступен для записи      | Переход в режим только чтения с плашкой                               |

Просмотр различий — простой построчный diff, без слияния. Полноценный merge в v1 не делаем: он создаёт больше способов потерять данные, чем решает.

### 9.5. Создание файлов

⌘N создаёт файл в текущей папке дерева, сразу открывает в редакторе, имя редактируется инлайн. Опция `rename_file_from_h1` (по умолчанию **выключена**) переименовывает файл по первому заголовку H1 — поведение в духе Bear, но выключено по умолчанию, потому что неожиданное переименование файлов пугает.

### 9.6. Живое превью: инкрементальный рендер

Это самая нагруженная часть приложения. Полный ре-рендер документа на 1 MB на каждое нажатие клавиши гарантированно даст лаг.

```
правка в редакторе
   ▼ дебаунс 120 ms, не чаще раза за кадр
текст + диапазон изменения → render_incremental
   ▼
blocks.rs: пересчитать разбиение на блоки верхнего уровня
   ▼
сравнить blake3 каждого блока со снимком предыдущего состояния
   ▼
BlockPatch[] { index, op: Replace|Insert|Delete, html }
   ▼
UI: заменить только затронутые <section data-block="N">
```

- Типичная правка внутри абзаца затрагивает один блок → ~3–8 ms сквозного времени.
- Правка, меняющая структуру (открытие fenced-блока), может затронуть хвост документа — считаем честно, но патчим только реально изменившееся.
- **Инвариант:** результат инкрементального рендера побайтово равен полному. Property-тест обязателен (`proptest`: случайный документ + случайная правка ⇒ инкрементальный == полный).
- **Страховка:** раз в 2 секунды простоя сверяется хеш всего документа; при расхождении — полный ре-рендер и запись в лог. Пользователь не должен видеть рассинхронизацию, даже если в диффе есть баг.
- Mermaid-блоки не пере-рендерятся, если их исходник не изменился (кэш по хешу, § 6).

### 9.7. Синхронный скролл

- Каждый блок в превью несёт `data-src-line`.
- Скролл редактора → превью: находим блок с ближайшей строкой, доводим по пропорции внутри блока.
- Скролл превью → редактор: обратное отображение.
- Флаг «ведущей» панели с таймаутом 100 ms — иначе получим петлю обратной связи и дрожание.
- Отключается в настройках (`sync_scroll`).

## 10. История и откат

### 10.1. Что это и чем это не является

Снимки версий документов: посмотреть, что было раньше, и вернуться назад. Это **не** система контроля версий — нет веток, нет слияния, нет истории по строкам. Задача ровно одна: текст, который однажды существовал, не должен исчезать безвозвратно.

Уровни защиты в приложении выстроены так, и каждый закрывает свой горизонт:

| Уровень       | Горизонт                              | Механизм                             |
| ------------- | ------------------------------------- | ------------------------------------ |
| Undo          | Текущая сессия, каждое нажатие        | История CodeMirror, в памяти         |
| Черновики     | До первой успешной записи             | `~/.1537paperstreet/drafts/` (§ 9.3) |
| **История**   | **Дни и месяцы, осмысленные границы** | **Snapshot-store (эта секция)**      |
| Корзина macOS | Удалённые файлы                       | Системная                            |

### 10.2. Хранилище: один внутренний store на все проекты машины

```
~/.1537paperstreet/history/
├── objects/<ab>/<blake3>.zst          общий на все проекты, content-addressed
├── projects/<blake3(canonical_path)>.sqlite   индекс снимков одного проекта
└── gc.state                            отметка последней сборки мусора
```

**Объекты — общие, индексы — раздельные.** Это даёт лучшее из обоих подходов:

- Дедупликация работает **между** проектами. Один и тот же шаблон, логотип или скопированная заметка в пяти проектах хранятся один раз. У людей с десятками проектов из общих папок это не мелочь.
- Сборка мусора одна на всё, а не N независимых. Один глобальный потолок по диску вместо арифметики по проектам.
- Удаление проекта — это удаление одного файла индекса. Объекты подберёт GC.
- Битый индекс одного проекта не роняет остальные.

**Индекс именуется хешем канонического пути, а не ULID проекта.** Следствие: пользователь удалил проект из списка, через месяц добавил ту же папку заново — история подхватилась. Если бы ключом был `project.id`, повторное добавление дало бы новый ULID и история осиротела бы. При переносе проекта («Найти папку заново», FR-2) индекс переименовывается.

**Сборка мусора — mark-and-sweep, без счётчиков ссылок.** GC обходит все индексы, собирает множество достижимых хешей, удаляет остальное. Счётчики ссылок пришлось бы поддерживать при каждой операции, они дрейфуют при сбоях, и это отдельный источник багов. Обход 10 млн строк занимает секунды, а GC запускается редко (при простое, не чаще раза в час) — цена приемлемая, а свойство самовосстановления бесплатное.

**Целостность:** blake3 проверяется при чтении. Не совпал — снимок помечается как утраченный, показывается в списке как недоступный, приложение продолжает работать. Одна повреждённая запись не должна ломать панель истории.

**Конкурентность:** SQLite в режиме WAL, единственный писатель обеспечен advisory-lock'ом одной инстанции (§ 4.3).

### 10.3. Когда делается снимок

Не на каждое автосохранение. Снимок раз в 800 мс — это 500 версий файла на 1 МБ за час работы, и никому не нужно откатываться на сорок секунд назад: для этого есть undo.

Снимки делаются на осмысленных границах и, что важнее, **перед каждой разрушительной операцией**:

| Триггер                                   | Код причины              | Что спасает                                      |
| ----------------------------------------- | ------------------------ | ------------------------------------------------ |
| Закрытие файла                            | `close`                  | Состояние на конец работы                        |
| 5 минут непрерывного редактирования       | `interval`               | Промежуточные вехи                               |
| Явное ⌘S                                  | `manual`                 | Точку, которую человек счёл важной               |
| Перед отправкой в Корзину                 | `pre_trash`              | Файл целиком                                     |
| Перед «Загрузить с диска» при конфликте   | `pre_conflict_discard`   | Версию, которую пользователь только что отбросил |
| Перед перезаписью диска своей версией     | `pre_conflict_overwrite` | Версию с диска                                   |
| Перед восстановлением черновика           | `pre_draft_restore`      | Текущее состояние буфера                         |
| Перед восстановлением из истории          | `pre_restore`            | Состояние до отката — откат тоже обратим         |
| Перед заменой при копировании/перемещении | `pre_replace`            | Затираемый файл                                  |

Нижние шесть строк — самая ценная и самая дешёвая часть фичи. Каждая из них это момент, где человек может нажать не туда и потерять текст навсегда. Снимок стоит порядка 10 мс и закрывает весь класс «ой, я не то нажал».

Снимок пропускается, если хеш содержимого совпадает с последним снимком этого файла.

### 10.4. Прореживание и лимиты

| Возраст    | Что остаётся                       |
| ---------- | ---------------------------------- |
| < 24 часов | Все снимки                         |
| < 7 дней   | По одному на час                   |
| < 90 дней  | По одному на день                  |
| Любой      | Закреплённые (`pinned`) — навсегда |

### 10.5. Восстановление

- Перед любым восстановлением делается снимок текущего состояния (`pre_restore`). Откат обратим.
- Запись идёт через тот же `docio::write_doc` (§ 9.3) — атомарно, с сохранением BOM, EOL и прав доступа.
- Альтернатива перезаписи: **«Скопировать в новый файл»** → `имя (2026-08-12 14-03).md` рядом с оригиналом. Часто это то, чего человек хочет на самом деле.
- **Удалённые файлы восстанавливаются из истории**, даже когда файла на диске уже нет и Корзина очищена. Панель истории проекта показывает удалённые пути отдельным разделом.

### 10.6. Побочная выгода: трёхсторонний конфликт

Со снимком на `base_hash` у нас появляется общий предок. Диалог конфликта (§ 9.4) перестаёт быть выбором между двумя непонятными файлами и начинает показывать раздельно: **что изменил ты** и **что изменили снаружи**.

Само слияние в v1 по-прежнему не делаем — выбор одной стороны. Но данные для настоящего трёхстороннего merge с этого момента есть, и в v1.1 это становится вопросом UI, а не архитектуры.

### 10.7. Приватность и удаление

- История содержит пользовательский текст. Она никогда не попадает в логи и **по умолчанию не включается в ZIP-экспорт** (есть отдельная опция).
- «Remove from list» не трогает ни файлы, ни историю — это отдельные вещи, и объединять их было бы сюрпризом. Явное удаление истории — команда **«Забыть историю проекта»** в настройках, с показом занимаемого объёма.
- Экран настроек показывает, сколько места занимает история по проектам, и позволяет чистить адресно.
- Отключение истории (`enabled: false`) прекращает запись, но не удаляет накопленное — за удалением нужно прийти явно.

### 10.8. Что сюда не входит

Git-бэкенд отложен в v1.1 сознательно. Идея писать снимки в приватный ref (`refs/1537paperstreet`) через временный индекс хороша: объекты живут в репозитории пользователя, `git log` и `git diff` работают, а HEAD, ветка, индекс и хуки не затронуты. Но она помогает только тем, у кого папка проекта — репозиторий, и содержит львиную долю пограничных случаев: `/usr/bin/git` на чистой машине это заглушка, запускающая установщик Xcode CLT; вложенные репозитории; Git LFS; гонки за `index.lock`. Универсальное хранилище стоит выпустить первым.

Как страховка и путь наружу в v1 есть одноразовая команда **«Экспортировать историю проекта в git-репозиторий»**: она создаёт обычный репозиторий с коммитом на каждый снимок. Пользователь не заперт в нашем формате.

## 11. Дизайн и темы

### 11.1. Визуальный язык

Ориентир — Bear: три колонки, воздух, типографика как главный элемент, минимум хрома. **Собственная реализация**: не копируем ассеты, иконки, шрифты и точные цвета Bear.

## 12. Производительность: как достигаем и как проверяем

**Настройки сборки** (профиль release):

```toml
[profile.release]
opt-level = 3
lto = "fat"
codegen-units = 1
panic = "abort"
strip = "symbols"
```

**Приёмы:**

- Ленивая инициализация всего тяжёлого (`SyntaxSet`, темы syntect, CodeMirror, Mermaid, KaTeX).
- Никаких блокирующих операций в главном потоке — файловый I/O через `spawn_blocking`.
- Списки виртуализированы (проекты и дерево); редактор виртуализирует вьюпорт сам.
- `content-visibility` для чанков документа.
- Инкрементальный рендер вместо полного при живом превью (§ 9.6).
- Автосохранение не блокирует ввод: сериализация буфера и запись уходят в фоновый поток.
- Стартовый путь: окно показывается сразу с последней сохранённой геометрией и темой из конфига.

**Регресс-контроль в CI:** `criterion` на `ps-core`/`ps-render` + `hyperfine` на старт. Падение производительности > 10 % относительно baseline из `main` → CI красный. Baseline в `benches/baseline.json`.

**Профилирование перед релизом:** Instruments (Time Profiler, Allocations, Leaks); Safari Web Inspector (Timelines для скролла и ввода); `cargo-bloat` для размера бинарника.

## 13. Безопасность

- **CSP:** `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' asset: data:; connect-src 'self'`. Никаких удалённых источников.
- **Санитайзинг:** сырой HTML в Markdown по умолчанию чистится `ammonia` (whitelist тегов/атрибутов, `javascript:` и `data:` в `href` запрещены). Это особенно важно в режиме Split: пользователь печатает — рендер идёт непрерывно, и любая дыра эксплуатируется по мере набора текста.
- **Asset protocol:** `scope` ограничен корнями зарегистрированных проектов, обновляется динамически.
- **Запись файлов** проходит через тот же `fsops::resolve`, что и чтение. Импорт вставленных изображений — тоже.
- **Внешние ссылки** (`http(s)://`) открываются в системном браузере, не в WebView.
- **Нет телеметрии.** Ни одного исходящего запроса, кроме опциональной проверки обновлений и **локального ACP-процесса**, который пользователь сам добавил в Settings (ADR-010). Приложение не вызывает LLM API и не ставит агентов из ACP Registry.
- **Логи** — в `~/.1537paperstreet/logs/`, ротация, без содержимого документов; только пути и коды ошибок. Черновики и история содержат пользовательский текст — они лежат отдельно, в логи не попадают и не включаются в ZIP-экспорт по умолчанию.
- `cargo audit`, `cargo deny`, `npm audit` в CI.

## 14. Тестирование

Цель по покрытию: **≥ 85 % строк для `ps-core` и `ps-render`**, ≥ 60 % для `ps-app`, ≥ 70 % для логики UI. Проверяется `cargo-llvm-cov` и `vitest --coverage`, порог фиксируется в CI.

### 14.1. Юнит-тесты (Rust)

`tempfile` для изолированной ФС. Обязательные сценарии: миграции схемы, битый JSON, конфликты имён, конкурентная запись конфига, natural sort, slug-генерация.

### 14.2. Тесты записи документов — критический блок

Потеря пользовательского текста — самый дорогой баг в этом продукте.

- Round-trip: открыть и сохранить без правок ⇒ файл **побайтово** не изменился (LF, CRLF, с BOM, без BOM, без финального перевода строки, права `0644` и `0600`).
- `kill -9` во время сохранения не оставляет ни битого файла, ни потерянных данных.
- Сохранение при отсутствии прав, при заполненном диске, при отключённом томе ⇒ черновик создан, баннер показан.
- Восстановление черновиков после имитации сбоя.
- Конфликт: файл изменён на диске между открытием и сохранением ⇒ запись **не** происходит, возвращается `Conflict`.
- Автосохранение не срабатывает, если байты не изменились.

### 14.3. Property-тесты (`proptest`)

- `fsops::resolve` никогда не возвращает путь вне корня — для любой строки на входе.
- **Инкрементальный рендер == полный рендер** для случайного документа и случайной правки. Минимум 10 000 кейсов.
- Slug всегда даёт валидное имя файла.
- Round-trip serde для конфига и проектов.

### 14.4. Snapshot-тесты рендера (`insta`)

Корпус в `crates/ps-render/tests/corpus/`: подмножество CommonMark, GFM-таблицы, сноски, чек-листы, mermaid, математика, вложенные списки, сырой HTML, битый Markdown, документ 5 MB, кириллица + эмодзи + RTL. Изменение вывода требует явного `cargo insta review`.

### 14.5. E2E — важное ограничение

`tauri-driver` **не работает на macOS**: WKWebView не поддерживает WebDriver. Поэтому:

- **UI-тесты** — Playwright против фронтенда в браузере с мок-слоем IPC (`ui/src/lib/ipc.mock.ts`).
- **Backend-тесты** — интеграционные тесты Rust, вызывающие те же функции, что и команды Tauri.
- **Ручной smoke-чеклист** перед релизом (`docs/release-checklist.md`): вибрантность, traffic lights, Корзина, диалоги, нотаризация, IME (ввод на японском/китайском в редакторе), диктовка, системная проверка орфографии.

### 14.6. Fuzzing

`cargo-fuzz` на `ps-render::render`, `ps-render::incremental` и `fsops::resolve`. Ночные прогоны в CI, найденные краши — в корпус регрессий.

## 18. Не входит в v1

Явно зафиксировано, чтобы агенты не начинали это делать по своей инициативе:

- WYSIWYG-редактирование (в v1 — исходник с подсветкой и живое превью).
- Vim/Emacs-режимы, сниппеты, шаблоны.
- История версий и снапшоты документов.
- Совместное редактирование.
- Полнотекстовый поиск по содержимому всех файлов (v1.1).
- Полноценное трёхстороннее слияние при конфликте версий (в v1 — выбор одной из сторон; данные для merge уже есть, § 10.6).
- Git-бэкенд для истории и интеграция со статусом git в дереве (v1.1, § 10.8).
- Windows и Linux.
- Синхронизация, облако, аккаунты, шаринг.
- Плагины и пользовательские скрипты (кроме opt-in ACP CLI, ADR-010).
- Экспорт в PDF/HTML (v1.1 — только ZIP).
- Wiki-ссылки: рендер `[[Note]]` / `[[Note|label]]` в превью есть; панель backlinks — v1.1.
- Множественные окна (v1.1). Вкладки документов и workspace-вкладки Assistant / Dashboard уже в v1.

| ----------------------------------------------------------- | ----------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **Потеря пользовательского текста при автосохранении**      | **Критич.** | Атомарная запись, проверка хеша перед записью, черновики, снимок перед каждой разрушительной операцией, тест `kill -9`, round-trip побайтово |
